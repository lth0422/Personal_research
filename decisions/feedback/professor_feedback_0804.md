# 교수님 피드백 0804 정리

> 대상 문서: `manuscript/개인_연구_주제_구체화_문서_v1_5.md`
> 정리일: 2026-08-04

## 1. 피드백 요약

### 1.1 데드라인 산정 근거

- `D = W/f_s`를 사용하는 이유를 상세히 설명해야 함.
- `W`와 `H`를 분리한 뒤에도 `D_i = W_i/f_s`를 사용할 것인지 재검토 필요.
- 샘플링 주파수 `f_s = 8 kHz`를 고정할 것인지 연구 범위를 명시해야 함.

### 1.2 실행시간과 모델 구조

- 실행시간이 `W`에 의존한다는 설명은 특정 모델 구조에 종속될 수 있음.
- FRFconv-TDSNet에서 관찰한 `C(W)` 관계를 다른 모델에 일반화하지 않아야 함.
- 초기 구현에서 모델을 고정하더라도 최종 주장의 실용성과 일반성을 위해 여러 베어링 결함 진단 모델을 조사하고 대표 모델로 검증할 필요가 있음.

### 1.3 Window와 Hop의 관계

- 새로 도입한 `H`의 의미와 기존 `W`와의 관계를 명확히 설명해야 함.
- `H<W`인 중첩 window와 `H=W`인 비중첩 window를 timeline 그림으로 제시하면 이해에 도움이 됨.

### 1.4 해결하려는 challenge와 중요성

- 현재 문서는 기존 연구와 다른 요소를 나열하지만, 기존 기법으로 해결되지 않던 문제가 무엇인지 명확하지 않음.
- 여러 기존 요소를 결합했다는 사실보다 어떤 conflict 또는 failure mode를 해결하는지가 먼저 제시돼야 함.
- 교수님 예시 논증:
  - 이상 징후가 커질 때 더 정밀한 진단과 더 잦은 진단이 동시에 필요할 수 있음.
  - 정밀한 진단은 실행시간의 증가를, 잦은 진단은 주기의 감소를 유발하므로 이용률 측면에서 충돌이 커짐.
  - 부하를 줄이기 위해 진단 주기만 늘리면 상태 인지가 느려질 수 있음.
  - `W`와 `H`를 독립 축으로 두고 runtime에 선택하며 전환의 실행 가능성을 검증하는 논증이 필요함.

## 2. 피드백에 대한 판단

- 핵심 지적은 novelty가 조합의 희소성으로만 서술되고, 해결 대상인 문제와 기존 방식의 실패 조건이 앞에 나오지 않는다는 것임.
- 본 연구의 중심 문제는 단순히 `(W,H,M)`을 함께 조절하는 것이 아님.
- 중심 문제 후보:
  - 이상 상태에서 진단 정보량 또는 모델 성능을 높이고 진단 간격을 줄이려는 요구가 동시에 발생할 수 있음.
  - 이용률은 `U=C(W,M)/T=C(W,M)f_s/H`이므로 `C` 증가와 `H` 감소가 동시에 일어나면 부하가 두 방향에서 증가함.
  - 고전 period-only elastic scheduling은 `H`를 늘려 부하를 낮출 수 있지만 진단 빈도와 적시성을 함께 낮춤.
  - window-only 또는 model-only adaptation은 입력 정보량, 진단 빈도와 실행 가능성의 관계를 함께 다루지 못함.

## 3. 확인된 사실과 연구 가설의 구분

### 3.1 현재 확인된 사실

- KCC 조건에서 `W`가 커질수록 FRFconv-TDSNet의 실행시간과 이용률이 증가했음.
- `W=1024`, `W=2048` 조건은 비중첩 주기에서 이용률이 1 이상이었음.
- 기존 서베이에서 period, window, model을 각각 조절하는 접근은 확인했으나 vibration anomaly와 runtime slack을 함께 사용해 `W/H/M`을 고르는 사례는 현재 범위에서 확인되지 않았음.

### 3.2 아직 검증해야 할 연구 가설

- H1: 이상 징후가 커질수록 더 짧은 진단 주기, 즉 더 작은 `H`가 실제 진단 지연 또는 이상 구간 recall에 유리함.
- H2: 기계 상태에 따라 가장 적합한 `W` 또는 `M`이 달라짐.
- H3: H1과 H2를 동시에 만족시키려 하면 `U=C(W,M)f_s/H`가 증가해 고정 정밀 모드 또는 q-only 정책이 deadline miss를 일으킬 수 있음.
- H4: 제안 정책이 fixed, q-only, slack-only, period-only 방식보다 deadline constraint를 유지하면서 이상 구간의 진단 성능 또는 진단 지연을 개선함.

> H1과 H2가 실험에서 확인되지 않으면 기계 상태 기반 `(W,H,M)` adaptation의 필요성이 약해진다. 이 경우 연구 범위와 주장을 재설정해야 한다.

## 4. 기존 접근의 실패 조건

| 기존 접근 | 가능한 장점 | 해결하지 못하는 문제 |
| --- | --- | --- |
| fixed-light | deadline 여유 확보 | 이상 상태에서 필요한 진단 성능 또는 진단 빈도를 제공하지 못할 수 있음 |
| fixed-precise | 높은 정보량·모델 성능 유지 | 부하 또는 간섭이 커지면 deadline miss와 job backlog 가능 |
| period-only elastic | `H`를 늘려 이용률 감소 | 진단 빈도와 상태 인지 속도도 함께 감소 |
| window-only | `W`를 줄여 실행시간 감소 가능 | 진단 빈도 `H`와 상태별 정보 요구를 독립적으로 반영하지 못함 |
| model-only | accuracy–latency trade-off 조절 | 입력 시간 범위와 진단 주기를 다루지 않음 |
| q-only | 기계 상태에 맞는 정밀 모드 요청 | 현재 시스템에서 실행 가능한지 확인하지 않음 |
| slack-only | deadline 여유에 맞춰 부하 조절 | 이상 상태에서 필요한 진단 성능과 적시성을 구분하지 않음 |

## 5. 제안 방법의 대답

- `W`: 한 번의 진단이 보는 신호의 시간적 맥락과 입력 정보량
- `H`: 진단 job의 release 주기와 상태 갱신 빈도
- `M`: 입력으로부터 진단 결과를 만드는 모델 구조 또는 구성
- 기계 상태 `q`: 상태별 최대 진단 주기와 후보 모드의 진단 성능 순위를 정함.
- 시스템 여유 `S`: 현재 실행 가능한 후보 집합을 제한함.
- 정책은 무조건 `W`를 키우고 `H`를 줄이지 않음. 상태별 실제 진단 성능과 timing profile을 바탕으로 feasible mode 중 가장 적합한 모드를 선택함.

핵심 대답 초안:

> 이상 상태에서는 더 빠른 상태 갱신과 더 높은 진단 성능이 동시에 요구될 수 있으나, 전자는 `H` 감소로 주기를 줄이고 후자는 `W` 또는 `M`에 따른 실행시간을 늘려 이용률을 두 방향에서 증가시킨다. Period-only adaptation은 부하를 줄이기 위해 `H`를 늘리지만 상태 인지를 늦출 수 있고, window-only 또는 model-only adaptation은 진단 빈도와 실행 가능성을 함께 다루지 못한다. 본 연구는 `W`, `H`, `M`을 독립 축으로 둔 이산 mode bank를 구성하고, anomaly state가 요구 성능과 최대 진단 주기를 정하며 runtime slack이 feasible mode를 제한하도록 역할을 분리한다. 제안 정책의 유효성은 deadline miss를 제한하면서 이상 구간의 진단 정확도, recall 또는 진단 지연을 개선하는지로 검증한다.

## 7. 아직 결정할 점

- 이상 상태에서 필요한 진단 성능을 accuracy, anomaly recall, detection delay 중 무엇으로 정의할지
- `D_app(q)`를 도출할 application-level 근거를 어떤 데이터 또는 물리 모델에서 확보할지

- empirical schedulability와 formal schedulability 중 학위논문의 최종 보장 수준
- 모드 전환 중 carry-over job과 transient overload를 어떻게 처리할지
